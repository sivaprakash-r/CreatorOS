# CreatorOS — Key Design Decisions

| # | Decision | Why | Trade-off |
|---|---|---|---|
| D1 | **One gateway module for all AI calls** (`app/mesh/client.py`, OpenAI SDK pointed at `api.meshapi.ai/v1`) | Mesh is mandatory; a single choke point makes the rule auditable (grep for `OpenAI(` finds one place) and lets us log every call | Model-specific features (e.g. Anthropic tool schemas) are not used; JSON mode is requested where supported and parsed defensively |
| D2 | **LangGraph `StateGraph` with a conditional edge** rather than a for-loop | The brief asks for named nodes and a real loop; the graph is inspectable (`get_graph()`) and tested structurally | A plain loop would be shorter; LangGraph adds a dependency |
| D3 | **Editor scores, code decides** — the verdict is derived from the score vs. `EDITOR_PASS_SCORE` and the hard character limit, not from the model's own "accept" | Consistent, auditable, testable loop control; prevents the model from accepting an over-limit post | Threshold is a global knob; could be per-brand later |
| D4 | **Editor never rewrites** — it emits numbered, verifiable required edits; the writer revises and returns a change log | Keeps agents genuinely distinct and makes the trail readable (request ↔ change) | Two calls per round instead of one |
| D5 | **Decisions are written as they happen** through a `Sink` with its own DB sessions | UI can show live progress; a crash mid-pipeline still leaves the partial trail | Slightly more DB round-trips |
| D6 | **Learning = deterministic statistics + LLM distillation** | Stats are reproducible evidence (stored on the run); the LLM turns them into actionable rules with confidence; both are shown in the UI | With few posts, n is small — confidence is surfaced rather than hidden |
| D7 | **Learnings are injected as prompt context (rules + engagement table), newest cycle replaces the old one** | Simple, transparent, provably changes the prompt (unit-tested); superseded rules stay in the DB for audit | Not a numerical policy / bandit; a weighting scheme would need far more data than a hackathon produces |
| D8 | **Engagement score weights comments/shares/saves over likes and normalises by impressions** | Matches how platforms rank; comparable across posts of different reach | Weights are opinionated constants |
| D9 | **Transparent engagement simulator** (`simulate_metrics`) that rewards hooks, CTA, concreteness, structure, with noise | Lets the loop run end-to-end without credentials and makes Experiment B fair (same model before/after) | It is a model, not reality; real X metrics are supported and preferred when configured |
| D10 | **Quality measure CQS = rules + embedding voice similarity + independent LLM judge** | Combines cheap deterministic checks with a semantic judge; the judge prompt differs from the editor's so the system does not grade itself with the same lens | LLM-judge noise; mitigated with temperature 0 and six explicit criteria |
| D11 | **Brand voice = LLM profile + measured style stats** | Numbers (emoji/post, chars/post, list usage) anchor the profile and let the editor/judge check concrete fit | Profile is re-learned wholesale on new samples (no incremental update) |
| D12 | **Platform specs in code** (`platforms.py`) shared by writer, editor, scorer and simulator | One source of truth for limits/conventions; multi-platform adaptation is per-piece with its own spec | Adding a platform means editing code, not config |
| D13 | **Visual = image-model background (Mesh) + typeset headline (Pillow)** | Image models render lettering unreliably; the headline must match the piece, so the visual agent designs a *background-only* prompt plus headline/subline/palette and `poster.py` composes the brand chip + text. If the image call fails a procedural gradient is used and the error is recorded in the decision — a visual always exists | Posters share one layout; no retry of the image model yet |
| D18 | **Best-slot recommendation from evidence** | `scheduling.py` picks the hour with the best mean engagement once ≥3 published posts with metrics exist, else platform defaults; the reason is stored on the `scheduled` decision whether accepted or overridden | Hour-of-day only; no day-of-week learning yet |
| D19 | **Every agent decision carries its gateway calls** (`payload.llm`: model, tokens, latency) | Makes the Mesh usage auditable per piece and feeds the Agent log / totals in the UI | Call attribution is per pipeline run; concurrent runs share one client |
| D14 | **APScheduler in-process polling the DB** | Zero extra infrastructure; survives restarts because the queue is the `content_pieces` table | Single replica only (documented) |
| D15 | **Postgres in compose, SQLite everywhere else** | Judges can `docker compose up`; tests and local dev need no DB server | `create_all` instead of migrations at this stage |
| D16 | **Mock mode for tests, loudly labelled** | Deterministic, free CI; the brief penalises faked features, so the mock is confined to tests, the UI shows a red banner, and startup refuses a missing key otherwise | Mock text is simple; real-model behaviour is evaluated separately |
| D17 | **Vanilla single-file frontend** | Fast to ship, nothing to build, served by FastAPI; Playwright tests target `data-testid`s | No component framework; fine at this size |
| D20 | **Replay is rendered from the stored trail, not re-run** | The piece page can step through strategist → writer → editor → … using the persisted decisions and versions, so judges can watch the run without spending Mesh credits, and the replay is guaranteed to match what actually happened | Timing is uniform (1.8 s/step), not the real latency |
| D21 | **Platform previews are derived from the final text** | LinkedIn fold at 210 chars, X 280-char counter, Instagram carousel split on paragraphs / list items with the hook as slide 1, blog article view — same text, platform-true rendering | Previews are approximations of each platform's UI |
